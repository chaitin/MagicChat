# 用户资料缓存与活动时间合并写入

用户资料和活动时间采用不同的持久化方式，不依赖 Redis。

## 用户资料

`account.Service` 为鉴权和个人资料读取提供进程内缓存。缓存保存 `Account` 原始资料字段（包括未经过昵称显示策略处理的昵称），不保存密码散列、session token 或鉴权结果。每项有效期为一分钟，最多保留 20,000 个用户，超过容量按最近使用顺序淘汰；同一用户的并发缓存未命中会合并加载。等待其他请求加载资料时可响应 context 取消，取到加载锁后也会重新检查请求状态。

昵称、头像等修改仍先提交数据库，再失效缓存。用户自行修改、管理员修改、第三方登录同步资料及账号注销都接入本进程缓存失效。加载期间发生失效时，旧查询不能重新填入缓存。

每次鉴权依然通过一条数据库查询检查 session 存在、有效期和用户启用状态，同时读取用户资料的 `updated_at` 和当前昵称策略。缓存版本不匹配时重新加载完整资料，因此其他实例更新资料后，下一次鉴权也会重新加载。返回资料时应用本次查询得到的昵称策略，不把策略的显示结果写回缓存。

单独调用 `GetProfile` 时，完整资料走缓存，昵称策略通过一次轻量查询读取。因此策略切换无须等待资料缓存过期；其他实例修改普通资料字段时，独立 `GetProfile` 调用仍由缓存过期兜底。

此缓存不替代联系人、群成员等业务列表查询。它们仍沿用原有查询和权限规则。

## 活动时间

鉴权产生的 session `last_seen_at` 和心跳产生的用户 `last_online_at` 先记录在内存中。同一个 ID 只保留最新时间。后台任务每分钟刷一次，每批最多更新 500 行；活动更新不改变用户资料的 `updated_at`。

刷盘时保留待写记录，数据库提交成功后才清除已确认的时间。刷盘期间收到的新时间仍留到下一轮，失败批次会重试。SQL 只更新仍存在的记录，并且只推进时间，避免旧实例的延迟写入覆盖新时间，也不会恢复已注销的 session。

本进程个人资料读取会叠加尚未刷盘的在线时间。其他数据库读取看到的活动时间可能滞后一轮。每种活动缓冲最多保存 100,000 个 ID；容量用尽时跳过新的 ID，并由后台任务汇总告警，避免数据库长期不可用时内存无限增长。

## 生命周期

生产入口使用带活动后台任务的 router 构造函数。正常退出时先停止接收请求，等待活动任务停止，再进行最后一次刷盘；主进程等待该步骤结束。Compose 为 server 保留 30 秒退出时间。

没有持久化队列：进程崩溃或被强制终止时，尚未刷盘的活动时间会丢失；数据库写入持续失败时，丢失窗口可能超过一分钟。昵称、头像等已经返回修改成功的资料已在数据库中，不依赖这次刷盘。

## 验证

本地测试覆盖缓存命中、并发加载、版本刷新、修改后失效、缓存容量、即时注销/禁用/过期检查、并发时间合并、批量大小、失败重试、正常退出刷盘，以及真实 PostgreSQL 的时间类型和单调更新条件。PostgreSQL 测试使用 `POSTGRES_TEST_DSN` 指向独立测试数据库，并创建临时 schema；不要将它指向生产环境。
